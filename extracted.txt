CHAPTER 1: INTRODUCTION
SkillGrid is a browser-based, MERN-stack (MongoDB, Express.js, React.js, Node.js) web application that bridges the gap between local daily-wage workers — electricians, plumbers, painters, carpenters, and similar skilled professionals — and clients in their vicinity who need such services. It replaces informal, word-of-mouth hiring with a transparent, digital marketplace where clients can discover verified workers, book them directly, track the status of their request, chat with the worker in real time, and confirm job completion through a secure OTP-based mechanism.
The platform is built around three distinct roles — Client, Worker, and Admin — each with a dedicated dashboard and a specific set of capabilities. Clients can browse and search for workers by profession, raise a booking request, communicate with the assigned worker, and mark the job as completed once it is finished at their premises. Workers can manage incoming requests, accept or decline them, update their professional profile (charges, experience, service photos), and generate a one-time completion code once the work is done. Administrators oversee the platform by monitoring registered users, removing accounts that violate policy, and reviewing feedback submitted through the Contact Us page.
Traditional hiring of local workers in India is largely informal — clients rely on neighbours, local shopkeepers, or personal networks to find a plumber or an electrician, with no way to verify credentials, compare charges, or track whether a request was even seen. This creates inefficiency for clients and lost opportunities for workers who are equally skilled but lack visibility. SkillGrid directly targets this gap by digitizing the discovery, booking, communication, and completion-verification workflow end-to-end, while remaining lightweight enough to be usable by workers with limited digital literacy.
The system was designed and implemented entirely using the MERN stack, chosen specifically because it is a JavaScript-only stack (both frontend and backend), which keeps the codebase consistent, is well-documented, has a large open-source ecosystem, and — importantly for an academic project — is the stack most actively expected of BCA/MCA graduates entering the industry today.
1.1 Theoretical Background
The theoretical foundation of SkillGrid draws from four areas: NoSQL database design, RESTful API architecture, modern frontend engineering with React, and real-time communication using WebSockets. Each of these is discussed below in the context of how it was actually applied in the project.
1.1.1 The MERN Stack
MERN is an acronym for MongoDB, Express.js, React.js, and Node.js — four technologies that together form a complete, JavaScript-based full-stack web development framework:
MongoDB — A document-oriented NoSQL database used to persist all application data (users, service requests, chat messages, contact submissions) as flexible, JSON-like BSON documents.
Express.js — A minimal and unopinionated web framework running on Node.js, used in SkillGrid to define all REST API routes (/api/auth, /api/workers, /api/requests, /api/admin, /api/contact, /api/messages) and to attach authentication and file-upload middleware.
React.js — A component-based JavaScript UI library used to build the entire client-side single-page application, including role-specific dashboards, the booking modal, and the live chat window.
Node.js — A JavaScript runtime built on Chrome’s V8 engine that allows the same language (JavaScript) to be used on both client and server, and that hosts the Express API and the Socket.IO real-time server in this project.
Choosing a single-language stack significantly reduced context-switching during development — data models defined with Mongoose schemas on the backend map naturally onto the JSON objects consumed by React components on the frontend, with no serialization mismatch.
1.1.2 Database Design with MongoDB
SkillGrid’s database is organized into four Mongoose collections, each modelled as a schema with strict field types and validation:
User — stores both clients and workers in a single collection, differentiated by a role field (client / worker / admin). Worker-specific fields such as profession, experience, chargeType, chargeAmount, rating, and jobsCompleted remain undefined for client accounts, taking advantage of MongoDB’s flexible schema.
Request — represents a single booking between a client and a worker, tracking its lifecycle through a status field (pending → accepted / rejected → completed) and carrying a completionOtp used to verify that the work was actually finished.
Message — stores individual chat messages tied to a specific Request via requestId, enabling per-booking chat history rather than one global chat.
Contact — stores messages submitted through the public Contact Us form, with an isRead flag for the admin panel.
References between collections (e.g. Request.client and Request.worker pointing to User._id) are implemented using Mongoose’s ObjectId references and resolved at query time using .populate(), which avoids data duplication while still allowing a single query to return joined data — for example, fetching a client’s bookings along with the assigned worker’s name, phone, and photo in one call.
1.1.3 RESTful API Design with Express.js
The backend exposes a set of stateless REST endpoints grouped by resource. Each route file under backend/routes/ is mounted on the Express app with a distinct base path, keeping the API modular and easy to extend:

Protected routes are secured using a custom checkauth middleware that verifies a JSON Web Token supplied in the auth-token request header, and admin-only routes additionally pass through an isAdmin middleware that checks the decoded user’s role before allowing the request to proceed.
1.1.4 Authentication and Security
User passwords are never stored in plain text — they are hashed using bcrypt.js (via bcryptjs) with a randomly generated salt before being persisted to MongoDB. On successful login, the server issues a signed JSON Web Token (JWT) containing the user’s id and role, which the client stores and attaches to subsequent requests. This makes the API stateless: the server does not need to maintain session data, since every request carries its own proof of identity.
Registration additionally requires email-based OTP verification before an account can be created. A six-digit OTP is generated on the server, emailed to the user via Nodemailer over Gmail SMTP, and verified server-side (moved from an earlier, less secure client-side check) before a short-lived registration token is issued — this token, not the raw email, is what authorizes the final /register call, closing off a class of attacks where a malicious client could bypass OTP verification entirely.
1.1.5 Real-Time Communication with Socket.IO
Because coordinating a service booking often requires back-and-forth conversation (confirming timing, address, or the exact issue), SkillGrid includes a real-time chat feature built on Socket.IO. Each booking gets its own chat "room", identified by the Request’s MongoDB _id. Clients and workers join this room from their respective dashboards, and messages are broadcast only to participants of that specific booking.
A key security concern with WebSocket-based chat is that, unlike HTTP requests, a socket connection is typically opened once and reused — so authentication has to happen at the connection (handshake) stage rather than per message. SkillGrid’s server verifies the JWT during the Socket.IO handshake itself (io.use middleware) and derives the sender’s identity (id, name) from the verified token on the server side, rather than trusting a senderId sent by the client — preventing a user from impersonating another participant in the chat.
1.1.6 File Uploads and Cloud Storage
Profile photos and worker portfolio images are handled using Multer, a Node.js middleware for handling multipart/form-data. In the current, deployment-ready version of the project, uploads are streamed directly to Cloudinary via multer-storage-cloudinary rather than being written to local disk — this was a deliberate architectural change made during the deployment-preparation phase, since platforms like Render use ephemeral filesystems where locally saved files would be lost on every redeploy or restart.
1.2 Objectives of the Project
The overall goal of SkillGrid is to design and implement a functional, secure, and deployable web platform that digitizes the process of finding, booking, and paying local skilled workers. The specific objectives are:
Role-Based Access: Provide distinct, secure portals for Clients, Workers, and Admins, with route-level protection so that each role can only access functionality relevant to it.
Verified Registration: Ensure every account is tied to a real, accessible email address through server-side OTP verification before the account is created.
Efficient Worker Discovery: Allow clients to browse and evaluate available workers by profession, experience, rating, and charges.
Streamlined Booking Workflow: Let clients raise a service request in a few clicks and let workers accept or decline it instantly from a live dashboard.
Real-Time Communication: Enable direct, authenticated chat between a client and worker for the duration of a specific booking.
Verifiable Job Completion: Use a one-time password, generated by the worker and entered by the client, to confirm that work was genuinely completed on-site — protecting both parties from false completion claims.
Data Security: Protect user credentials with password hashing, protect API endpoints with JWT authentication, and protect uploaded media using cloud storage rather than an exposed local directory.
Usable Feedback: Replace intrusive browser alert() popups with a custom, non-blocking toast notification system for a smoother user experience.
Production Readiness: Prepare the application for real-world deployment — externalized configuration, environment-based API URLs, dynamic CORS, and cloud-hosted media and database.
1.3 Need of the Study
The need for a platform like SkillGrid arises directly from the inefficiencies of informal local hiring, which this project set out to document and address before development began:
1.3.1 Reasons for the Study
Lack of Discoverability: Skilled workers without a shopfront or personal network in a new area struggle to find clients, even when demand for their skill exists nearby.
No Transparency: Clients have no easy way to compare workers by experience, rating, or charges before committing to hire someone.
Unverifiable Completion: In informal arrangements, disputes commonly arise over whether a job was actually finished as agreed, with no neutral record of completion.
Communication Friction: Coordinating timing, address, and the specific issue over phone calls is inefficient compared to a persistent, in-context chat thread tied to the booking.
No Central Record: Neither party has a history of past bookings, making it hard for a client to re-hire a worker they were satisfied with, or for a worker to demonstrate a track record.
Studying and implementing a structured digital platform directly resolves each of these — giving workers a visibility channel, giving clients a transparent comparison and booking mechanism, and giving both parties a verifiable, chat-backed record of every booking.
1.4 Scope of the Project
1.4.1 Functional Scope
User Management: Registration with OTP verification, login with JWT, role-based access (client / worker / admin), profile view and update, profile photo upload.
Worker Discovery: Public listing of all registered workers with profession, experience, rating, and charges.
Booking & Request Management: Create a booking request, view incoming requests (worker side), accept/decline, view sent bookings (client side), track status.
Real-Time Chat: Per-booking chat room between client and worker, backed by persisted chat history.
Completion Verification: OTP generation by the worker, OTP entry by the client, automatic increment of the worker’s completed-job count.
Admin Panel: View all non-admin users, delete a user account, view and manage Contact-Us submissions.
Contact Us: A public feedback form that stores submissions for admin review.
1.4.2 Non-Functional Scope
Security: Hashed passwords, JWT-protected routes, server-verified OTPs, JWT-authenticated Socket.IO connections, and server-derived (not client-supplied) chat sender identity.
Usability: A custom toast notification system replacing native browser alerts, responsive layouts for both dashboards.
Maintainability: Centralized API configuration (config.js) rather than hardcoded URLs scattered across components, so the same codebase runs against localhost in development and a deployed backend in production.
Deployability: Environment-variable-driven configuration for MongoDB Atlas, JWT secret, Cloudinary credentials, and CORS origins, prepared for a Render (backend) + Vercel (frontend) deployment.
Out of scope: In-app payment processing, worker background verification, geolocation-based matching, and native mobile applications were kept out of scope for this academic version of the project.

CHAPTER 2: PROBLEM ANALYSIS
Problem analysis is the process of understanding the real-world difficulties faced by the intended users of a system, and translating those difficulties into concrete, buildable requirements. Before writing a single line of code for SkillGrid, the informal, word-of-mouth process by which most local workers are currently hired was examined to identify exactly where it breaks down for clients and for workers.
2.1 Problems Identified
2.1.1 Limited Discoverability for Workers
Workers with genuine skill and experience but no personal network in an area receive little to no work, purely because clients have no way of finding them.
There is no central, searchable listing of available local workers by profession.
2.1.2 Lack of Transparency for Clients
Clients cannot compare workers by experience, rating, or charges before deciding whom to hire.
There is no way to see a worker’s track record (e.g. number of jobs completed) before booking.
2.1.3 Inefficient Request and Response Handling
A phone call to a worker may go unanswered or unnoticed, with no structured way for the client to know whether the request was seen at all.
Workers juggling multiple potential clients over calls/SMS have no single place to view, accept, or decline pending work.
2.1.4 Communication Friction
Coordinating the exact address, issue description, and timing over an unstructured phone call is slower and more error-prone than a persistent, in-context text conversation.
2.1.5 Unverifiable Job Completion
Once a worker leaves, there is no neutral, recorded confirmation that the job was actually completed to the client’s satisfaction, which can lead to payment disputes.
2.1.6 Security and Data Handling Risks (identified during the project’s own security review)
Sensitive routes left unprotected would allow any client of the API to read or modify data without authentication.
OTP verification performed only on the client side can be trivially bypassed by a malicious user, since the check never touches the server.
Storing uploaded photos on local disk breaks in typical cloud deployments, where the filesystem is ephemeral and wiped on every redeploy.
Trusting a client-supplied sender identity in chat messages would let one user impersonate another in a conversation.
2.2 Proposed Solution — SkillGrid
SkillGrid addresses each of the problems above with a specific, corresponding feature, summarised below.
2.2.1 Discoverability and Transparency
A public "Browse Workers" listing (GET /api/workers/all) surfaces every registered worker with their profession, experience, rating, and charges, letting clients compare before booking.
2.2.2 Structured Booking and Response Workflow
Clients raise a structured booking request (service needed, address, date) that instantly appears on the worker’s dashboard.
Workers can Accept or Decline with a single action, and the client sees the status update immediately.
2.2.3 In-Context Real-Time Chat
Once a booking exists, client and worker get a dedicated Socket.IO chat room scoped to that request, with persisted history, so coordination happens in one place rather than over calls.
2.2.4 OTP-Verified Completion
When the job is finished, the worker generates a short numeric code; the client enters this code to mark the job completed. This gives both sides a clear, mutually-agreed completion event and increments the worker’s completed-jobs count.
2.2.5 Security Hardening
All sensitive routes are protected by JWT-based checkauth middleware, with an additional isAdmin guard for admin-only routes.
OTP verification for registration was moved fully to the backend, and a short-lived registration token now gates the final account-creation call.
Socket.IO connections are authenticated at the handshake stage using the same JWT, and the server — not the client — determines the sender’s identity for every chat message.
Profile photo and portfolio uploads were migrated from local disk storage to Cloudinary, making uploaded media durable across redeployments.
2.3 Implementation Strategy
The project followed an iterative build-and-review approach rather than a single upfront design phase, which suited a solo, deadline-bound academic project:
Requirement Analysis — identify core features (auth, worker listing, booking, chat, admin) directly from the problems above.
System Design — define the MongoDB schema, REST API surface, and page/component structure before writing backend logic.
Incremental Development — build and manually verify one module at a time (auth → worker listing → booking → dashboards → chat → admin panel), rather than attempting the whole system at once.
Security Audit Pass — once the core features worked, a dedicated review pass was done to find and close authentication, authorization, and data-handling gaps (see Section 2.1.6 for what it uncovered).
Deployment Preparation — externalize configuration, migrate file storage to the cloud, and configure CORS, in preparation for hosting on Render and Vercel.
2.4 Benefits of the Proposed System
Faster Matching: Clients find and book a suitable worker in minutes instead of relying on personal contacts.
Fair Visibility for Workers: Any registered worker is discoverable by any client in the system, independent of personal networks.
Clear Accountability: The status lifecycle (pending → accepted/rejected → completed) and OTP-based completion give both sides a shared, unambiguous record of the booking.
Reduced Communication Overhead: Persistent, per-booking chat replaces repeated phone calls for coordination.
Stronger Data Protection: Authenticated, role-checked APIs and cloud-hosted media reduce the risk of unauthorized data access or lost uploads.
CHAPTER 3: SYSTEM IMPLEMENTATION DETAILS
This chapter describes the methodology followed while building SkillGrid, and lists the concrete hardware and software environment used during development.
3.1 Methodology Adopted
3.1.1 Requirement Gathering
Since this is a solo academic project, requirements were derived directly from the problem analysis in Chapter 2 rather than formal stakeholder interviews: what data needs to exist (users, requests, messages), what actions each role needs to perform, and what security guarantees are non-negotiable (password hashing, protected routes, verified email).
3.1.2 System Design
Database Schema Design: Four Mongoose schemas (User, Request, Message, Contact) were designed first, since almost every feature depends on how data is shaped and related.
API Design: REST endpoints were grouped by resource (auth, workers, requests, admin, contact, messages) under separate Express routers, each mounted at its own base path in server.js.
Frontend Component Design: The React app was split into role-specific dashboards (ClientDashboard, WorkerDashboard, AdminDashboard) plus shared components (Navbar, Footer, BookingModel, LiveChat, Profile) so that UI logic for each role stays isolated.
3.1.3 Database Design
MongoDB Atlas (cloud-hosted) is used instead of a local MongoDB instance, so the same connection string works in both development and production via an environment variable (MONGO_URI).
Mongoose schemas enforce field types, required fields, and enumerated values (e.g. role: client|worker|admin, status: pending|accepted|rejected|completed) at the application layer.
References between collections (Request.client, Request.worker, Message.requestId, Message.senderId) are resolved at query time with .populate() rather than duplicating user data into every request document.
3.1.4 Frontend Development
Built with React.js using functional components and hooks (useState, useEffect, useContext).
Routing is handled with react-router-dom, including a custom PrivateRoute wrapper that redirects unauthenticated users and enforces role-based access (allowedRoles prop) on protected pages.
Global toast notifications are provided via a custom ToastContext, replacing browser alert() calls used earlier in development.
API base URL and file/photo URLs are resolved through a single config.js module (API_URL, getPhotoUrl) rather than being hardcoded per component — this was one of the key changes made during deployment preparation.
3.1.5 Backend Development
Built with Node.js and Express.js 5, exposing versionless REST routes under /api/*.
Mongoose is used as the ODM layer between Express route handlers and MongoDB Atlas.
checkauth middleware verifies the JWT on every protected route; isAdmin middleware additionally restricts admin-only routes.
Multer, backed by multer-storage-cloudinary, handles multipart file uploads and streams them directly to Cloudinary.
Socket.IO is attached to the same HTTP server as Express, with its own JWT-verifying handshake middleware, so chat and REST traffic share one deployable Node process.
3.1.6 Integration
Frontend and backend were integrated over a REST API secured with CORS, restricted to an explicit allow-list of origins (localhost during development, the deployed Vercel URL in production) rather than a wildcard.
API endpoints were manually tested with Postman/Thunder Client before being wired into the corresponding React components.
3.1.7 Testing
Manual functional testing was performed for each module — registration/OTP, login, worker browsing, booking, accept/decline, chat, OTP completion, admin actions — after implementation.
A dedicated security-focused testing pass was carried out late in development, specifically probing for unprotected routes, client-side-only checks, and trust boundaries in the chat system (see Chapter 2, Section 2.1.6).
3.1.8 Deployment (Preparation)
Hardcoded API URLs across components are being centralized into config.js with environment variables (REACT_APP_API_URL) so the same build works against localhost or the deployed backend.
CORS origins are read from an environment variable (FRONTEND_URL) rather than being hardcoded, so the backend can be pointed at a new frontend deployment without a code change.
File storage has been migrated from local disk to Cloudinary to survive redeployments on platforms with ephemeral filesystems.
Target hosting: Render for the Node/Express/Socket.IO backend, Vercel for the React frontend build.

CHAPTER 5: IMPLEMENTATION
This chapter walks through how SkillGrid was actually built, module by module, starting from the project setup and ending with the deployment-preparation changes made after the initial feature-complete version. Screenshot placeholders are left at the points where a reader would expect to see the running application; these should be replaced with actual screenshots captured from the live app before final submission.
5.1 Setting Up the Development Environment
Installed Node.js (LTS) and set up a project root folder locals/ containing two subfolders: backend/ and frontend/.
Initialized the backend with npm init and installed express, mongoose, cors, dotenv, bcryptjs, jsonwebtoken, multer, socket.io, cloudinary, multer-storage-cloudinary, and nodemailer.
Scaffolded the frontend with Create React App and installed react-router-dom, socket.io-client, and @emailjs/browser.
Created a MongoDB Atlas cluster and stored the connection string in a backend/.env file as MONGO_URI, alongside JWT_SECRET, EMAIL_USER/EMAIL_PASS, and Cloudinary credentials — none of these are hardcoded in source.
5.2 Backend Development
5.2.1 Server Bootstrap (server.js)
The Express app and a raw Node http server are created together, and the same http server instance is handed to both Express (for REST) and Socket.IO (for real-time chat) — this is what allows a single Node process, and a single Render deployment, to serve both. CORS is restricted to an explicit list of allowed origins built from a hardcoded localhost entry and an environment-provided FRONTEND_URL, rather than a wildcard.
5.2.2 Database Connection (db.js)
connectDB() wraps mongoose.connect() in a try/catch, logging a clear success message on connect and calling process.exit(1) on failure so that a broken database connection fails loudly at boot rather than silently breaking every route later.
5.2.3 Schemas
Four Mongoose schemas were defined — User, Request, Message, and Contact — each described in Section 1.1.2. All four use { timestamps: true } so createdAt/updatedAt are tracked automatically.
5.2.4 Authentication Routes (routes/auth.js)
POST /send-otp — generates a 6-digit OTP, stores it server-side in an in-memory Map keyed by email with a 10-minute expiry, and emails it via Nodemailer.
POST /verify-otp — checks the submitted OTP against the stored record and, on success, issues a short-lived (10-minute) JWT "registration token" rather than simply returning true — this token is what the /register endpoint actually trusts.
POST /register — refuses to create an account unless a valid registration token is supplied, hashes the password with bcrypt before saving, and accepts an optional profile photo via Multer.
POST /login — verifies the password with bcrypt.compare and issues a 5-day JWT containing the user’s id and role.
GET/PUT /profile — protected by checkauth; lets a logged-in user fetch or update their own profile, including worker-only fields (profession, location, experience, chargeType, chargeAmount) and a new profile photo.
5.2.5 Worker Listing (routes/worker.js)
A single public GET /all endpoint returns every user with role: "worker", with the password field excluded via .select('-password').
5.2.6 Booking / Request Routes (routes/request.js)
POST /book — creates a new Request document from the logged-in client to a chosen worker.
GET /myrequest — returns all requests assigned to the logged-in worker, with client details populated.
PUT /updatestatus/:id — lets the assigned worker (and only that worker) accept or decline a request.
GET /mybookings — returns all requests raised by the logged-in client, with worker details populated.
POST /generate-otp/:id — lets the assigned worker generate a 4-digit completion OTP, but only once the request status is "accepted".
POST /verify-otp/:id — lets the assigned client submit the OTP; on a match, the request is marked completed and the worker’s jobsCompleted counter is incremented.










5.2.7 Admin Routes (routes/admin.js)
Both routes (GET /users, DELETE /user/:id) are protected by checkauth followed by isAdmin, so a non-admin JWT is rejected before the database is ever touched.

5.2.8 Contact & Messages Routes
routes/contact.js exposes a public POST /send for the Contact Us form, and admin-only GET /all, PUT /read/:id, DELETE /delete/:id for reviewing submissions. routes/message.js exposes a checkauth-protected GET /:requestId that verifies the requester is actually a participant (client or worker) of that booking before returning chat history.
5.2.9 Middleware
checkauth.js — reads the auth-token header, verifies it with jsonwebtoken, and attaches the decoded payload to req.user.
isAdmin.js — runs after checkauth and rejects the request with 403 unless req.user.role === 'admin'.
upload.js — configures Multer with CloudinaryStorage, restricting uploads to jpeg/jpg/png/webp and 5 MB, and auto-resizing to a 500×500 bound on upload.
5.2.10 Real-Time Chat (Socket.IO block in server.js)
The Socket.IO server’s io.use() handshake middleware verifies the client-supplied JWT before a connection is accepted, and looks up the user in MongoDB to attach a trusted { id, name, role } object to the socket. On send_message, the server builds the Message document using socket.user.id and socket.user.name — values it derived itself — rather than trusting anything the client sends for who the sender is, then broadcasts it to everyone in that booking’s room.

// Ceck JWT token verify before connecting socket 
io.use(async (socket, next) => {
    try {
        const token = socket.handshake.auth?.token;
        if (!token) return next(new Error('Authentication required'));
 
        const decoded = jwt.verify(token, process.env.JWT_SECRET);
        const user = await User.findById(decoded.user.id).select('name role');
        if (!user) return next(new Error('User not found'));
 
        socket.user = { id: user._id.toString(), name: user.name, role: user.role };
        next();
    } catch (err) {
        next(new Error('Invalid or expired token'));
    }
});
 
io.on('connection', (socket) => {
    console.log('User connected:', socket.id, '-', socket.user.name);
 
    socket.on('join_room', (requestId) => {
        socket.join(requestId);
        console.log(`Joined room: ${requestId}`);
    });
 
    socket.on('send_message', async (data) => {
        try {
            const newMsg = new Message({
                requestId:  data.requestId,
                senderId:   socket.user.id,     // ← client se nahi, verified token se
                senderName: socket.user.name,   // ← client se nahi, verified token se
                message:    data.message,
            });
            await newMsg.save();
 
            io.to(data.requestId).emit('receive_message', {
                _id:       newMsg._id,
                requestId: data.requestId,
                senderId:  socket.user.id,
                senderName:socket.user.name,
                message:   data.message,
                createdAt: newMsg.createdAt,
                time: new Date(newMsg.createdAt).toLocaleTimeString('en-IN', {
                    hour: '2-digit', minute: '2-digit'
                })
            });
 
        } catch (err) {
            console.error('Socket error:', err.message);
        }
    });
 
    socket.on('disconnect', () => {
        console.log('User disconnected:', socket.id);
    });
});
 
app.get('/', (req, res) => res.send("Server running..."));

router.post('/send-otp', async (req, res) => {
    try {
        const { email, name } = req.body;
        if (!email) return res.status(400).json({ message: 'Email is required' });
 
        const existing = await User.findOne({ email });
        if (existing) return res.status(400).json({ message: 'This email is already registered. Please login.' });
 
        const otp = Math.floor(100000 + Math.random() * 900000).toString();
        otpStore.set(email, { otp, expiresAt: Date.now() + 10 * 60 * 1000 });
 
        try {
            await sendOtpEmail(email, name, otp);
        } catch (mailErr) {
            console.error('Email send error:', mailErr.message);
            otpStore.delete(email);
            return res.status(500).json({ message: 'Failed to send OTP email. Please try again.' });
        }
 
        res.status(200).json({ message: 'OTP sent to your email' });
    } catch (err) {

    }

// STEP 2: OTP verify (backend)
router.post('/verify-otp', (req, res) => {
    try {
        const { email, otp } = req.body;
        const record = otpStore.get(email);
 
        if (!record) return res.status(400).json({ message: 'OTP expired or not requested. Please resend OTP.' });
        if (Date.now() > record.expiresAt) {
            otpStore.delete(email);
            return res.status(400).json({ message: 'OTP expired. Please resend OTP.' });
        }
        if (record.otp !== otp) return res.status(400).json({ message: 'Incorrect OTP.' });
 
        otpStore.delete(email);
 
        const regToken = jwt.sign({ email, purpose: 'register' }, process.env.JWT_SECRET, { expiresIn: '10m' });
        res.status(200).json({ message: 'OTP verified', regToken });
    } catch (err) {
        res.status(500).send('Server Error');
    }
});

router.post('/register', upload.single('photo'), async (req, res) => {
    try {
        const { name, email, password, phone, role, profession, experience, location, regToken } = req.body;
 
        // Security: No registration until OTP verified
        if (!regToken) return res.status(403).json({ message: 'Email verification required. Please verify OTP first.' });
 
        let decoded;
        try {
            decoded = jwt.verify(regToken, process.env.JWT_SECRET);
        } catch (err) {
            return res.status(403).json({ message: 'Verification expired. Please verify OTP again.' });
        }
        if (decoded.purpose !== 'register' || decoded.email !== email) {
            return res.status(403).json({ message: 'Email verification mismatch. Please verify OTP again.' });
        }
 
        const safeRole = (role === 'worker') ? 'worker' : 'client';
 
        let user = await User.findOne({ email });
        if (user) return res.status(400).json({ message: "User already exists with this email" });
 
        const salt = await bcrypt.genSalt(10);
        const hashedPassword = await bcrypt.hash(password, salt);
 
        user = new User({
            name,
            email,
            password: hashedPassword,
            phone,
            role: safeRole,
            profession: safeRole === 'worker' ? profession : undefined,
            experience: safeRole === 'worker' ? experience : undefined,
            location: safeRole === 'worker' ? location : undefined,
            photo: req.file ? req.file.path : ''
        });
 
        await user.save();
        res.status(201).json({ message: "Account created successfully" });
 
    } catch (error) {
        console.error("Register Error:", error.message);
        res.status(500).send("Server Error");
    }
});

const isAdmin = require('../middleware/isAdmin');
 
// POST — user sent message (public, no login needed)
router.post('/send', async (req, res) => {
    try {
        const { name, email, message } = req.body;
        if (!name || !email || !message)
            return res.status(400).json({ message: 'All fields are required' });
 
        const newContact = new Contact({ name, email, message });
        await newContact.save();
        res.status(201).json({ message: 'Message sent successfully!' });
 
    } catch (err) {
        console.error('Contact Error:', err.message);
        res.status(500).send('Server Error');
    }
});
 
// GET — all message seen by admin
router.get('/all', checkauth, isAdmin, async (req, res) => {
    try {
        const messages = await Contact.find().sort({ createdAt: -1 });
        res.json(messages);
    } catch (err) {
        res.status(500).send('Server Error');
    }
});
 
// PUT — admin message mark
router.put('/read/:id', checkauth, isAdmin, async (req, res) => {
    try {
        await Contact.findByIdAndUpdate(req.params.id, { isRead: true });
        res.json({ message: 'Marked as read' });
    } catch (err) {
        res.status(500).send('Server Error');
    }
});

import React, { createContext, useContext, useState, useCallback } from 'react';
import './Toast.css';
 
const ToastContext = createContext();
 
export const useToast = () => useContext(ToastContext);
 
let idCounter = 0;
 
export const ToastProvider = ({ children }) => {
  const [toasts, setToasts] = useState([]);
 
  const showToast = useCallback((message, type = 'info', duration = 3500) => {
    const id = ++idCounter;
    setToasts(prev => [...prev, { id, message, type }]);
    setTimeout(() => {
      setToasts(prev => prev.filter(t => t.id !== id));
    }, duration);
  }, []);
 
  const removeToast = (id) => {
    setToasts(prev => prev.filter(t => t.id !== id));
  };
 
  return (
    <ToastContext.Provider value={{ showToast }}>
      {children}
      <div className="toast-container">
        {toasts.map(t => (
          <div
            key={t.id}
            className={`toast-item toast-${t.type}`}
            onClick={() => removeToast(t.id)}
          >
            <span className="toast-icon">
              {t.type === 'success' ? '✅' : t.type === 'error' ? '❌' : 'ℹ️'}
            </span>
            <span className="toast-message">{t.message}</span>
          </div>
        ))}
      </div>
    </ToastContext.Provider>
  );
};

import React from 'react';
import { Navigate } from 'react-router-dom';
 
const PrivateRoute = ({ children, allowedRoles }) => {
  const token = sessionStorage.getItem('token');
  const userString = sessionStorage.getItem('user');
 
  if (!token || !userString || userString === 'undefined') {
    return <Navigate to="/login" replace />;
  }
 
  // allowedRoles is given theck the role
  if (allowedRoles && allowedRoles.length > 0) {
    try {
      const user = JSON.parse(userString);
      if (!allowedRoles.includes(user.role)) {
        return <Navigate to="/" replace />;
      }
    } catch (err) {
      return <Navigate to="/login" replace />;
    }
  }
 
  return children;
};
 
export default PrivateRoute;

const Login = () => {
  const navigate = useNavigate();
  const { showToast } = useToast();
  const [credentials, setCredentials] = useState({
    email: '',
    password: ''
  });
 
  const handleChange = (e) => {
    setCredentials({ ...credentials, [e.target.name]: e.target.value });
  };
 
  const handleSubmit = async (e) => {
    e.preventDefault();
    
    try {
      const response = await fetch(`${API_URL}/api/auth/login`, {
        method: "POST",
        headers: {
          "Content-Type": "application/json"
        },
        body: JSON.stringify(credentials)
      });
 
      const data = await response.json();
 
      if (response.ok) {
        showToast(data.message, 'success');

        showToast('Login Failed: ' + data.message, 'error');
      }

import React, { useState, useEffect, useRef } from 'react';
import { io } from 'socket.io-client';
import './LiveChat.css';
import { API_URL, getPhotoUrl } from '../config';
 
const LiveChat = ({ requestId, currentUser, otherUser, onClose }) => {
    const [messages, setMessages] = useState([]);
    const [inputMsg, setInputMsg] = useState('');
    const [loading, setLoading]   = useState(true);
    const messagesEndRef           = useRef(null);
    const socketRef                = useRef(null); // ← socket ref me rakho
    const token = sessionStorage.getItem('token');
 
    // ── Socket + History setup ────────────────────────────
    useEffect(() => {
        // 1. new socket connection
        socketRef.current = io((API_URL), {
    transports: ['websocket', 'polling'],
    auth: { token }
});
 
        // 2. Room join 
        socketRef.current.emit('join_room', requestId);
 
        // 3. Real-time message receive
        socketRef.current.on('receive_message', (data) => {
            setMessages(prev => {
                const exists = prev.some(m =>
                    m._id && data._id && m._id.toString() === data._id.toString()
                );
                if (exists) return prev;
                return [...prev, data];
            });
        });
 
        // 4. Chat history load 
        const fetchHistory = async () => {
            try {
                const res = await fetch(
                    `${API_URL}/api/messages/${requestId}`,
                    { headers: { 'auth-token': token } }
                );
                const data = await res.json();
                if (Array.isArray(data)) {
                    setMessages(data.map(msg => ({
                        ...msg,
                        time: new Date(msg.createdAt).toLocaleTimeString('en-IN', {
                            hour: '2-digit', minute: '2-digit'
                        })
                    })));
                }
            } catch (err) {
                console.error('History error:', err);
            } finally {
                setLoading(false);
            }
        };
 
        fetchHistory();
 
        // 5. Cleanup — component unmount 
        return () => {
            socketRef.current.disconnect();
        };
    }, [requestId, token]);
 
    // ── Auto scroll ───────────────────────────────────────
    useEffect(() => {
        messagesEndRef.current?.scrollIntoView({ behavior: 'smooth' });
    }, [messages]);
 
    // ── Send message ──────────────────────────────────────
    const sendMessage = () => {
        if (!inputMsg.trim() || !socketRef.current) return;
 
        const msgData = {
            requestId,
            senderId:   currentUser.id,
            senderName: currentUser.name,
            message:    inputMsg.trim(),
        };
 
        socketRef.current.emit('send_message', msgData);
        setInputMsg('');
    };
 
    const handleKeyDown = (e) => {
        if (e.key === 'Enter' && !e.shiftKey) {
            e.preventDefault();
            sendMessage();
        }
    };
 
    return (
        <div className="chat-overlay" onClick={onClose}>
            <div className="chat-box" onClick={(e) => e.stopPropagation()}   >
 
                {/* Header */}
                <div className="chat-header">
                    <div className="chat-header-info">
                        <img
                            src={otherUser?.photo
                                ? getPhotoUrl(otherUser.photo, otherUser.name)
                                : `https://ui-avatars.com/api/?name=${encodeURIComponent(otherUser?.name || 'U')}&background=fdb441&color=1a1a1a&bold=true`}
                            alt="user"
                            className="chat-header-avatar"
                            onError={(e) => {
                                e.target.src = `https://ui-avatars.com/api/?name=${encodeURIComponent(otherUser?.name || 'U')}&background=fdb441&color=1a1a1a&bold=true`;
                            }}
                        />
                        <div>
                            <h4>{otherUser?.name || 'User'}</h4>
                            <span className="chat-online">🟢 Online</span>
                        </div>
                    </div>
                    <button className="chat-close-btn" onClick={onClose}>✖</button>
                </div>
 
                {/* Messages */}
                <div className="chat-messages">
                    {loading ? (
                        <div className="chat-empty"><p>Loading messages...</p></div>
                    ) : messages.length === 0 ? (
                        <div className="chat-empty"><p>👋 Say hello to start the conversation!</p></div>
                    ) : (
                        messages.map((msg, index) => {
                            const isMe = msg.senderId?.toString() === currentUser.id?.toString();
                            return (
                                <div key={msg._id || index}
                                    className={`chat-msg-wrapper ${isMe ? 'me' : 'other'}`}>
                                    {!isMe && (
                                        <img
                                            src={`https://ui-avatars.com/api/?name=${encodeURIComponent(msg.senderName || 'U')}&background=1a1a2e&color=fdb441&bold=true`}
                                            alt="avatar"
                                            className="chat-msg-avatar"
                                        />
                                    )}
                                    <div className={`chat-bubble ${isMe ? 'bubble-me' : 'bubble-other'}`}>
                                        {!isMe && (
                                            <span className="chat-sender-name">{msg.senderName}</span>
                                        )}
                                        <p>{msg.message}</p>
                                        <span className="chat-time">{msg.time}</span>
                                    </div>
                                </div>
                            );
                        })
                    )}
                    <div ref={messagesEndRef} />
                </div>
 
                {/* Input */}
                <div className="chat-input-area">
                    <textarea
                        className="chat-input"
                        placeholder="Type a message... (Enter to send)"
                        value={inputMsg}
                        onChange={(e) => setInputMsg(e.target.value)}
                        onKeyDown={handleKeyDown}
                        rows={1}
                    />
                    <button className="chat-send-btn" onClick={sendMessage}>➤</button>
                </div>
 
            </div>
        </div>

CHAPTER 7: CONCLUSION
SkillGrid successfully demonstrates a complete, working solution to the problem of informal, hard-to-discover local service hiring, built end-to-end on the MERN stack. Over the course of this project, a full authentication system with server-verified OTP registration, a role-based booking workflow, a JWT-authenticated real-time chat system, an OTP-based job-completion mechanism, and an admin panel were designed, implemented, tested, and hardened.
Beyond the core features, a dedicated security-review pass — carried out once the application was functionally complete — proved to be one of the most valuable parts of the project. It surfaced real, exploitable gaps: routes that were reachable without authentication, OTP verification that could be bypassed because it only ran on the client, and a chat system that would have trusted a client-supplied identity for each message. Fixing these, along with replacing intrusive browser alerts with a proper toast system and moving file storage to Cloudinary ahead of deployment, took the project from "working on my machine" to something genuinely closer to production-ready.
Enhanced Efficiency: The platform automates the entire workflow from worker discovery to verified job completion, removing the friction of phone-call-based coordination and giving both clients and workers a persistent, structured record of every booking.
Improved Trust: Verified registration, transparent worker profiles, and OTP-confirmed completion give both parties confidence that the other side of the transaction is accountable.
Real-Time Interaction: Socket.IO-based chat, scoped per booking and authenticated at the handshake, allows fast, secure coordination without exposing users to identity-spoofing risks.
Scalable Foundation: A cloud-hosted database (MongoDB Atlas), cloud-hosted media (Cloudinary), and environment-driven configuration mean the same codebase can move from a developer’s laptop to a public deployment (Render + Vercel) without structural changes.
Overall, this project reinforced practical, industry-relevant skills — schema design, REST API security, WebSocket authentication, and deployment engineering — well beyond what a purely theoretical treatment of the MERN stack would have provided, and produced a platform that genuinely could serve real clients and workers in a local community.
CHAPTER 8: FUTURE SCOPE
SkillGrid was deliberately scoped to be achievable within a single academic term while still being a genuinely useful, secure application. Several extensions were identified during development but consciously deferred; they are documented here as a roadmap for future work on the platform.
8.1 Payments and Monetization
Integrated in-app payments (e.g. Razorpay/Stripe) so clients can pay workers directly through the platform rather than offline.
Optional platform commission or subscription model for workers seeking greater visibility.
8.2 Trust and Verification
Government ID / skill-certificate verification for workers before their profile goes live.
A rating-and-review system populated by clients after a completed job, rather than a static rating field.
8.3 Discovery and Matching
Geolocation-based worker search ("workers within 5 km") using the browser Geolocation API and MongoDB geospatial queries.
A recommendation layer that surfaces previously-booked or highly-rated workers first.
8.4 Communication and Notifications
Push notifications (web push / mobile) for new booking requests and chat messages, rather than requiring the dashboard to be open.
Read receipts and typing indicators in the chat window.
SMS-based OTP as a fallback channel for workers without reliable email access.
8.5 Platform and Scale
A dedicated analytics dashboard for the admin — bookings over time, most-requested professions, completion rates.
Horizontal scaling of the Socket.IO layer (e.g. with a Redis adapter) if concurrent chat load grows beyond a single Node process.
A native mobile app (React Native) reusing the existing REST API and Socket.IO backend.
8.6 Emerging Technology Integration
AI-assisted matching that suggests the most suitable worker based on the client’s described issue.
Automated fraud/spam detection on the Contact Us and registration flows.
CHAPTER 9: LIMITATIONS
While SkillGrid meets its core objectives, the following limitations are acknowledged honestly, both as scope boundaries of this academic submission and as a checklist for anyone extending the project.
9.1 Technical Limitations
No automated test suite (unit/integration) — all functional and security testing was performed manually.
The in-memory OTP store (a JavaScript Map) used for registration OTPs is not persisted, so it resets if the server restarts, and does not scale across multiple server instances without an external store such as Redis.
Chat does not currently support message delivery/read receipts, file attachments, or offline push notifications.
No automated backup/monitoring pipeline has been configured for the production MongoDB Atlas cluster.
Deployment (Render + Vercel) was being configured at the time of writing and had not yet been load-tested under concurrent users.
9.2 Functional Limitations
No in-app payment processing; transactions are assumed to happen offline between client and worker.
Worker skill/identity claims are self-declared at registration and are not independently verified by the platform.
No geolocation-based matching — clients currently browse all workers rather than being shown the nearest ones first.
Single-language (English) interface only.
9.3 Project-Level Limitations
Built and maintained by a single developer within a fixed academic deadline, which constrained the number of features and the depth of testing that could be undertaken.
As a final-year academic project, several production concerns (rate limiting, structured logging, automated CI/CD) were consciously left for future iterations rather than attempted under time pressure — see Chapter 8 for the full roadmap.
